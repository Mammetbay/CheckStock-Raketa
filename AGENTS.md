# AGENTS.md — Архитектура ИИ-оркестрации и правила разработки (CheckStock / Ракета)

Настоящий документ определяет инженерный регламент использования ИИ-агентов (Main Orchestrator + специализированные Subagents) при разработке и верификации прототипа **CheckStock** (складское ядро экосистемы снабжения **«Ракета» v0.5**).

> **Принцип ответственности (из ТЗ CheckStock):**
> *«ИИ можно использовать, чтобы уложиться в один день. Технические решения и проверка результата остаются за разработчиком».*
> ИИ-агенты в проекте работают не в режиме «сгенерировать шаблонный код», а в рамках строгой модульной архитектуры (**Deep Modules**), где инварианты предметной области, схема транзакций и приёмочные тесты зафиксированы человеком-архитектором.

---

## 1. Контекст документов заказчика и связь с системой «Ракета»

Агенты обязаны опираться на три авторитетных источника в репозитории:
1. **`docs/task/CheckStock-testovoe-zadaniye.pdf`** — техническое задание на прототип складского учёта (экран остатков, склады и движения, отправки FBS/FBO, история операций, обработка нехватки, удаление ФФ с остатком, защита от двойного списания).
2. **`docs/task/Raketa_TZ_kratkoe_v05.pdf`** — целевая архитектура веб-системы снабжения «Ракета» (единая база остатков и поставок в пути, расчётное ядро прогнозов и закупок, запрет двойного учёта одного физического остатка, сохранение спроса при шортаже).
3. **`docs/ARCHITECTURE.md`** — технический дизайн (TDD / ADR-001..003), описывающий схему БД, конечные автоматы состояний и закон сохранения товара.

### Как решения CheckStock закладывают фундамент для «Ракеты» v0.5:
- **Запрет двойного учёта остатка (`Raketa v0.5, стр. 3, 5`):** разделение остатка на `physical_qty`, `available_qty`, `reserved_fbs_qty` и отдельные статусы `IN_TRANSIT_FF`, `IN_TRANSIT_FBO`, `SHIPPED_FBS` гарантирует, что ни одна единица товара не будет посчитана дважды при агрегации по складам или артикулам.
- **Прозрачная фиксация дефицита (`Shortage`):** когда на выбранном ФФ не хватает `available_qty`, система не скрывает потребность и не уводит остаток в минус, а формирует детерминированный план покрытия дефицита (`ShortageResolutionPlan`) за счёт других ФФ (Split Fulfillment или межскладское перемещение).
- **Аудит и промышленная надёжность:** прототипы от бизнеса (созданные в т.ч. с помощью Codex) часто страдают от гонок данных (race conditions), потери истории при удалении справочников и повторных списаний при двойном клике. Данная архитектура устраняет эти риски на уровне ядра БД и доменного модуля.

## 2. Словарь проектирования: Deep Modules (`codebase-design`)

Во всех промптах, код-ревью и спецификациях используется единая терминология проектирования глубоких модулей:

- **Module (Модуль)** — программная единица с чётким **Interface** и скрытой **Implementation** (например, `LedgerModule` для всех складских движений). Мы избегаем размытых терминов «сервис» или «компонент», когда речь идёт о проектировании границ.
- **Interface (Интерфейс)** — всё, что вызывающая сторона (HTTP-роутер или тест) обязана знать для корректного вызова: сигнатуры команд, доменные инварианты, коды ошибок (`ShortageError`, `InvalidStateTransitionError`) и гарантии идемпотентности.
- **Implementation (Реализация)** — внутренняя логика модуля: блокировки строк `SELECT ... FOR UPDATE`, пересчёт `physical_qty = available_qty + reserved_fbs_qty`, запись в `stock_operations` и автоматическая сверка баланса (`Reconciliation Check`).
- **Depth (Глубина модуля)** — рычаг (leverage) на единицу интерфейса. **Deep Module** имеет компактный интерфейс (несколько атомарных команд движения товара), за которым скрыта вся сложность транзакционного учёта, идемпотентности и защиты от гонок. Поверхностные (shallow) pass-through прослойки запрещены.
- **Seam (Шов)** — место, где живёт интерфейс модуля и через которое мы можем подменить адаптер или прогнать полный набор тестов без изменения кода внутри модуля.
- **Adapter (Адаптер)** — конкретная реализация на шве (например, сессия PostgreSQL в продакшене и изолированная транзакционная тестовая БД `Local-substitutable` в Pytest).
- **Leverage (Рычаг) и Locality (Локальность)** — выгода от глубокого модуля: вызывающий код остаётся тривиальным, а все правила списания, резервирования и идемпотентности сосредоточены в одном месте.

## 3. Топология ИИ-агентов (Main Agent + Subagents)

Разработка и верификация разделены между **Главным агентом-оркестратором (Main Agent)** и тремя специализированными **субагентами (Subagents)**. Каждый субагент отвечает за свой слой и проверяется через фиксированный шов (**Seam**).

```text
┌─────────────────────────────────────────────────────────────────────────┐
│                    MAIN ORCHESTRATOR AGENT                              │
│  Роль: Архитектор, хранитель инвариантов (ADR-001..003) и приёмки ТЗ    │
│  Вход: CheckStock ТЗ + Ракета ТЗ v0.5 + docs/ARCHITECTURE.md            │
└───────────────┬─────────────────────────┬───────────────────────────────┘
                │                         │
                ▼                         ▼
┌───────────────────────────────┐ ┌───────────────────────────────────────┐
│ SUBAGENT 1: Ledger & Domain   │ │ SUBAGENT 2: Transport & Reactive UI   │
│ (Deep Module Implementation)  │ │ (FastAPI + Jinja2/Tailwind/JS)        │
├───────────────────────────────┤ ├───────────────────────────────────────┤
│ • Схема БД и CHECK-ограничения│ │ • Тонкие HTTP-хендлеры поверх Seam    │
│ • Атомарные движения и резервы│ │ • Единый экран: ФФ, В пути, Архив ФФ  │
│ • State Machine + Idempotency │ │ • Модальное окно разрешения Shortage  │
│ • Алгоритм Shortage Resolution│ │ • Управление ФФ (Soft Delete + перенос│
│ • Soft Delete ФФ с историей   │ │   остатка) и живой журнал операций    │
└───────────────┬───────────────┘ └───────────────────┬───────────────────┘
                │                                     │
                └─────────────────┬───────────────────┘
                                  ▼
┌─────────────────────────────────────────────────────────────────────────┐
│ SUBAGENT 3: Adversarial QA & Invariant Verifier (Red-Team)              │
│ Роль: Независимая проверка всех сценариев ТЗ через внешний интерфейс    │
├─────────────────────────────────────────────────────────────────────────┤
│ • 40% оценки: приход, резерв FBS, отправка/отмена FBS, перемещение ФФ,  │
│   отправка/приёмка FBO + проверка закона сохранения товара после шага   │
│ • 25% оценки: нехватка на выбранном ФФ при достаточном общем остатке,   │
│   удаление ФФ с остатком и историей, двойное подтверждение (идемпотент.)│
│ • 15% оценки: проверка чистоты репозитория, авто-сидинга и Docker-старта│
└─────────────────────────────────────────────────────────────────────────┘
```

### 3.1. Main Orchestrator Agent (Главный агент-оркестратор)
- **Зона ответственности:** декомпозиция задачи на проверяемые шаги (Steps 1–6), контроль соответствия `docs/ARCHITECTURE.md`, координация субагентов и финальный технический аудит.
- **Железные инварианты, которые контролирует Main Agent:**
  1. **Закон сохранения товара (Reconciliation Invariant):**
     $$\sum \text{Приходы (RECEIPT)} = \sum \text{physical\_qty (активные и архивные ФФ)} + \sum \text{IN\_TRANSIT\_FF} + \sum \text{FBO (IN\_TRANSIT + RECEIVED)} + \sum \text{SHIPPED\_FBS}$$
  2. **Инвариант узла ФФ:** для каждого склада и артикула всегда выполняется `physical_qty == available_qty + reserved_fbs_qty`, причём `available_qty >= 0` и `reserved_fbs_qty >= 0`.
  3. **Запрет каскадного удаления истории:** ни одна операция со складом ФФ не имеет права удалять строки из `stock_operations` или обнулять физический остаток.

### 3.2. Subagent 1 — Domain & Ledger Engine (`LedgerModule`)
- **Цель:** реализовать глубокий доменный модуль складского учёта (`app/models.py`, `app/schemas.py`, `app/ledger.py`, `app/seed.py`).
- **Правила реализации:**
  - Вся бизнес-логика сосредоточена внутри `LedgerModule`. Роутеры FastAPI не имеют права напрямую менять `available_qty` или `physical_qty` в обход интерфейса модуля.
  - Каждое подтверждение операции (`receive_transfer`, `ship_fbs_order`, `cancel_fbs_order`, `receive_fbo_shipment`) блокирует целевую строку и проверяет текущий статус. Повторный вызов для уже завершённой операции возвращает идемпотентный результат (`already_processed=True`) без повторного движения товара и без дублирования проводки в `stock_operations`.
  - Для операций создания (`record_receipt`, `create_transfer`, `create_fbs_reserve`, `create_fbo_shipment`) поддерживается `idempotency_key`: повторная отправка запроса с тем же ключом возвращает ранее созданную запись.
  - При нехватке `available_qty` на выбранном ФФ модуль анализирует остатки на всех остальных активных ФФ:
    - если суммарного доступного остатка по сети достаточно (`total_available >= requested_qty`), возвращает детализированный `ShortageResolutionPlan` с двумя готовыми действиями: **Split Fulfillment** (разбить отгрузку/резерв по складам) или **Transfer Missing Qty** (создать перемещение недостающего количества с ФФ-донора);
    - если товара не хватает даже суммарно по всем ФФ, возвращает чёткую ошибку глобального дефицита.

### 3.3. Subagent 2 — HTTP Transport & Operator Dashboard (`FastAPI + UI`)
- **Цель:** построить понятный, быстрый и наглядный веб-интерфейс менеджера (`app/main.py`, `app/templates/index.html`, `app/static/app.js`) и конфигурацию контейнеризации (`Dockerfile`, `docker-compose.yml`).
- **Требования к интерфейсу (по ТЗ CheckStock и UX-референсу «Ракеты»):**
  - **Блок 01 — Экран остатков и сверка баланса:**
    - Сводная матрица по каждому артикулу (`SKU-101`, `SKU-102`, `SKU-103`) и каждому ФФ (`Север`, `Юг` и др.): **Физически / Доступно / В резерве FBS**.
    - Отдельная наглядная панель: **В пути между ФФ**, **В пути / Принято на FBO**, **Отправлено клиенту по FBS**.
    - Индикатор математической сходимости остатков (`Сверка остатков: СХОДИТСЯ ✓`) в реальном времени.
    - Специальный блок **«Числится на удалённых (архивных) ФФ»**, который появляется, если склад был удалён с сохранением остатка на его архивном балансе (с кнопкой быстрого вывода остатка на действующий ФФ).
  - **Блок 02 — Склады и движения:**
    - Добавление, переименование и удаление ФФ (при удалении ФФ с остатком менеджер выбирает: оставить остаток числиться за архивным ФФ или сразу перевести свободный остаток на выбранный действующий ФФ).
    - Оформление прихода, отправки перемещения между ФФ и кнопка **«Принять перемещение»** (с защитой от двойного клика и демонстрацией идемпотентности).
  - **Блок 03 — Отправки FBS и FBO + обработка нехватки:**
    - Создание резерва FBS, кнопки **«Отправить клиенту»** и **«Отменить резерв»**.
    - Оформление отправки на маркетплейс по FBO и кнопка **«Принять на FBO»**.
    - Интерактивная панель разрешения нехватки: когда менеджер пытается зарезервировать под FBS или отправить по FBO больше, чем доступно на выбранном ФФ (например, `12 шт. SKU-101` с ФФ `Север`, где доступно `10 шт.`, а на `Юге` есть ещё `6 шт.`), интерфейс показывает раскладку и позволяет в 1 клик выполнить **Авто-разделение (10 + 2)** или **Создать перемещение на недостающие 2 шт.**.
  - **История операций:**
    - Полный журнал (`stock_operations`), где видно: время, тип операции, артикул, количество, откуда (`from_location`), куда (`to_location`), номер документа и комментарий.

### 3.4. Subagent 3 — Adversarial QA & Verification (`Pytest Red-Team`)
- **Цель:** доказать корректность работы каждого сценария автоматическими тестами (`tests/test_checkstock.py`) до сдачи проекта.
- **Принцип тестирования (`codebase-design`):**
  - **The interface is the test surface.** Тесты проверяют систему через публичный интерфейс модуля и HTTP API, а не через моки внутренних функций.
  - После **каждого** тестового сценария вызывается проверка инварианта `verify_reconciliation()` — ни один тест не считается успешным, если хотя бы по одному SKU нарушен баланс.

## 4. Пошаговый план разработки и контроля (Step-by-Step Pipeline)

Разработка ведётся строго по 6 шагам с обязательной верификацией каждого этапа:

1. **Шаг 1 — Спецификация ИИ-оркестрации (`AGENTS.md`) и структура проекта:**
   - Фиксация архитектуры глубоких модулей, ролей субагентов и инвариантов учёта.
   - Настройка зависимостей (`requirements.txt`), конфигурации БД (`app/database.py`) и чистой структуры пакетов.
2. **Шаг 2 — Слой данных, модели SQLAlchemy и начальные данные (`Seed`):**
   - Реализация таблиц `products`, `warehouses`, `warehouse_stocks`, `transfers`, `fbs_orders`, `fbo_shipments`, `stock_operations` с ограничениями целостности.
   - Автоматический идемпотентный сидинг начальных данных из ТЗ: магазин CheckStock, ФФ `Север` и `Юг`, `SKU-101 Органайзер` (10 / 6), `SKU-102 Контейнер` (5 / 0), `SKU-103 Корзина` (0 / 4).
3. **Шаг 3 — Глубокий доменный модуль учёта (`LedgerModule`):**
   - Реализация атомарных операций прихода, перемещений между ФФ, резервов/отправок/отмен FBS и поставок FBO.
   - Реализация идемпотентности (State Machine + `idempotency_key`), алгоритма `ShortageResolutionPlan`, мягкого удаления ФФ с сохранением остатков и истории, а также сверщика `check_reconciliation`.
4. **Шаг 4 — FastAPI эндпоинты и веб-интерфейс менеджера:**
   - Подключение REST API (`/api/dashboard`, `/api/warehouses`, `/api/receipts`, `/api/transfers`, `/api/fbs`, `/api/fbo`, `/api/reset-demo`) и интерактивного интерфейса на Jinja2 + Tailwind CSS + Vanilla JS.
5. **Шаг 5 — Автоматическое тестирование (`Pytest`) всех складских и граничных сценариев:**
   - Проверка 100% сценариев из ТЗ (включая нехватку на выбранном ФФ, удаление ФФ с остатком в двух режимах, повторное подтверждение перемещения/FBS/FBO и идемпотентность по ключу).
6. **Шаг 6 — Контейнеризация (`Docker Compose`) и документация (`README.md`):**
   - Сборка `Dockerfile` и `docker-compose.yml` для запуска одной командой.
   - Подготовка исчерпывающего `README.md` с описанием архитектурных решений, инструкцией по запуску, командами автотестов и пошаговым сценарием для записи 3–5 минутного демо-видео.

## 5. Чек-лист защиты от типичных ошибок («Что портит впечатление» в ТЗ)

Перед завершением работы Main Agent проверяет репозиторий по списку анти-паттернов из ТЗ:
- [x] **Никаких лишних и мусорных файлов** в корне проекта.
- [x] **Проект запускается строго по инструкции в `README.md`** (как через `docker compose up --build`, так и локально через `uvicorn` / `pytest`).
- [x] **`README.md` объясняет ключевые инженерные решения** (почему остатки сходятся, как устроена идемпотентность, как решена нехватка на выбранном ФФ, почему удаление ФФ не теряет остаток и историю), а не просто перечисляет кнопки.
- [x] **Все складские сценарии проверены автотестами и живыми запросами**, результаты сверки баланса (`Reconciliation Check`) равны `True` после каждой операции.
