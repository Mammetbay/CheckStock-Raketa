# Технический дизайн и архитектурные решения (TDD / ADR) — CheckStock

Документ описывает архитектуру прототипа **CheckStock**, модель складского учёта, обоснование выбора технологий и реализацию граничных сценариев (нехватка товара, удаление склада с остатком, защита от повторного подтверждения).

---

## 1. Цель системы и бизнес-контекст

Один артикул (SKU) одновременно может находиться на нескольких складах фулфилмента (ФФ), быть зарезервированным под заказы FBS или находиться в пути (между ФФ, на склад маркетплейса по FBO, к клиенту по FBS).

**Главная задача:** обеспечить прозрачный и математически строгий учёт товарных остатков и движений, при котором:
1. Менеджер на одном экране видит полную картину: **где товар, сколько доступно к продаже/отгрузке и что уже отправлено**.
2. Остатки гарантированно сходятся после любой операции.
3. Повторное нажатие кнопки подтверждения (сетевой ретрай, двойной клик) **никогда не списывает товар дважды**.
4. При удалении ФФ ни история операций, ни физический остаток не теряются.

## 3. Модель учёта остатков и движений (ADR-003)

Система использует **комбинацию материализованных остатков по узлам учёта и неизменяемого журнала операций (Immutable Ledger)**.

### 3.1. Состояния товара на складе ФФ (`WarehouseStock`)
Для каждой пары `(warehouse_id, product_id)` хранятся и контролируются ограничениями БД (`CHECK`):
- **`physical_qty`** — физически лежит на складе ФФ (`physical_qty = available_qty + reserved_fbs_qty`).
- **`available_qty`** — доступно для новых резервов FBS, отгрузок FBO и перемещений (`available_qty >= 0`).
- **`reserved_fbs_qty`** — заблокировано под открытые заказы FBS до их отправки или отмены (`reserved_fbs_qty >= 0`).

### 3.2. Учёт товара «В пути» и отгрузок (`Shipment / Transfer / FBSOrder`)
Любое движение за пределы доступного остатка переводит товар в явно отслеживаемый статус:
1. **`IN_TRANSIT_FF` (В пути между ФФ):** при отправке перемещения товар списывается с `physical_qty` и `available_qty` склада-отправителя и числится в пути на конкретный склад-получатель до момента **Приёмки перемещения**.
2. **`IN_TRANSIT_FBO` (В пути на маркетплейс по FBO):** при отправке FBO товар покидает ФФ и числится в пути на склад маркетплейса до подтверждения **Приёмки FBO** (после приёмки переходит в статус `DELIVERED_FBO` — принят маркетплейсом).
3. **`RESERVED_FBS` -> `SHIPPED_FBS` (К клиенту по FBS):**
   - **Резерв FBS:** уменьшает `available_qty`, увеличивает `reserved_fbs_qty` (`physical_qty` на ФФ не меняется).
   - **Отмена резерва FBS:** возвращает товар из `reserved_fbs_qty` обратно в `available_qty`.
   - **Отправка FBS:** списывает товар из `reserved_fbs_qty` и `physical_qty` на ФФ; заказ переходит в статус «В пути к клиенту по FBS» (`SHIPPED_FBS`).

### 3.3. Инвариант сходимости остатков (Закон сохранения товара)
После каждой транзакции для любого артикула выполняется равенство:
$$\text{Сумма всех приходов} = \sum \text{physical\_qty на всех ФФ} + \text{В пути между ФФ} + \text{В пути / доставлено по FBO} + \text{Отправлено клиентам по FBS}$$

В системе реализован автоматический сверщик (`Reconciliation Check`), который проверяет этот инвариант после каждого действия и отображает статус сходимости в интерфейсе.

## 4. Реализация ключевых сценариев (25% + 40% оценки)

### 4.1. Защита от повторного подтверждения (Идемпотентность)
Повторное нажатие кнопки «Принять перемещение», «Отправить FBS», «Принять FBO» или повторная отправка формы прихода не должны списывать или начислять товар дважды.
- **Решение 1 — Конечный автомат состояний (State Machine + `SELECT ... FOR UPDATE`):**
  Каждая сущность движения (перемещение, резерв FBS, поставка FBO) имеет строгий статус (`PENDING` / `RESERVED` / `IN_TRANSIT` / `COMPLETED` / `CANCELLED`). Перед сменой статуса строка блокируется в транзакции PostgreSQL через `SELECT ... FOR UPDATE`. Если статус уже `COMPLETED` (или `SHIPPED`), сервер **не выполняет повторное движение остатков**, а возвращает идемпотентный ответ с флагом `already_processed = true`.
- **Решение 2 — Ключ идемпотентности (`idempotency_key`):**
  Для операций создания (приход, новый резерв, новая отправка) поддерживается `idempotency_key` с уникальным индексом в таблице истории операций.

### 4.2. Нехватка товара на выбранном ФФ при достаточном общем остатке
**Сценарий:** На ФФ «Север» доступно 10 шт. `SKU-101`, на ФФ «Юг» — 6 шт. (общий доступный остаток = 16 шт.). Менеджер пытается зарезервировать под FBS или отправить по FBO **12 шт.** со склада «Север».
- **Решение:**
  1. Сервер определяет, что на выбранном ФФ не хватает `2 шт.`, но суммарного доступного остатка по сети ФФ (`16 шт.`) достаточно.
  2. Вместо тупой ошибки система возвращает структурированный план разрешения нехватки (`ShortageResolutionPlan`) с точной раскладкой по складам.
  3. В интерфейсе менеджеру сразу предлагаются **2 действия в один клик**:
     - **Вариант А — Авто-разделение по складам (Split Fulfillment):** списать/зарезервировать `10 шт.` с ФФ «Север» и недостающие `2 шт.` с ФФ «Юг» одной атомарной транзакцией.
     - **Вариант Б — Создать перемещение на недостающее количество:** автоматически оформить отправку перемещения `2 шт.` с ФФ «Юг» на ФФ «Север» для пополнения остатка.

### 4.3. Удаление ФФ с остатком и сохранением истории
**Требование ТЗ:** *«При удалении сохраните остатки и историю. Покажите, где числится товар»*.
- **Почему нельзя делать физический `DELETE`:** удаление записи склада из БД либо упадёт по внешнему ключу, либо каскадно уничтожит остатки и историю операций.
- **Решение:**
  1. **Мягкое удаление (Soft Delete / Архивация):** у склада выставляется флаг `is_deleted = true` и время `deleted_at`. Все прошлые записи в журнале операций сохраняют привязку к этому складу.
  2. **Два прозрачных режима работы с остатком при удалении ФФ:**
     - **Сохранение на балансе удалённого (архивного) ФФ:** если склад удаляется без мгновенного переноса, его текущие остатки (доступные и в резерве FBS) **не исчезают**, а отображаются на экране остатков в специальном блоке **«Числится на удалённых (архивных) ФФ»** с указанием бывшего склада (например, `Архив: ФФ Север`). Новые приходы на такой склад заблокированы, но с него можно в любой момент вывести (переместить) остаток на действующий ФФ.
     - **Удаление с одновременным переводом остатка:** при удалении менеджер также может сразу выбрать действующий ФФ-правопреемник, куда система автоматически зафиксирует операцию перевода свободного остатка с записью в историю операций.

## 5. Схема базы данных

1. **`products`** — `id`, `sku` (UNIQUE), `name`.
2. **`warehouses`** — `id`, `name`, `is_deleted` (bool), `deleted_at` (timestamp).
3. **`warehouse_stocks`** — `id`, `warehouse_id` (FK), `product_id` (FK), `physical_qty`, `available_qty`, `reserved_fbs_qty`, `UNIQUE(warehouse_id, product_id)`.
4. **`transfers`** (перемещения между ФФ) — `id`, `product_id`, `from_warehouse_id`, `to_warehouse_id`, `qty`, `status` (`IN_TRANSIT`, `RECEIVED`), `created_at`, `received_at`.
5. **`fbs_orders`** (резервы и отправки FBS) — `id`, `order_number`, `product_id`, `warehouse_id`, `qty`, `status` (`RESERVED`, `SHIPPED`, `CANCELLED`), `created_at`, `updated_at`.
6. **`fbo_shipments`** (отправки на маркетплейс по FBO) — `id`, `shipment_number`, `product_id`, `warehouse_id`, `qty`, `status` (`IN_TRANSIT`, `RECEIVED`), `created_at`, `received_at`.
7. **`stock_operations`** (единая история всех операций) — `id`, `idempotency_key` (UNIQUE, nullable), `operation_type`, `product_id`, `qty`, `from_location`, `to_location`, `reference_id`, `note`, `created_at`.

## 6. Начальные тестовые данные (Seed)

При первом старте автоматически создаются:
- **Магазин:** Основной магазин CheckStock
- **Склады ФФ:** `Север`, `Юг`
- **Тестовый приход (с записью в историю операций):**
  - `SKU-101` (Органайзер): Север = `10`, Юг = `6`
  - `SKU-102` (Контейнер): Север = `5`, Юг = `0`
  - `SKU-103` (Корзина): Север = `0`, Юг = `4`
